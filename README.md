# QSPICE_library

Библиотека поведенческих моделей компонентов для QSPICE с автоматической
проверкой каждой модели по даташиту.

Главная идея: **модель без стенда не существует**. Любая модель — это подгонка,
и единственный способ узнать, насколько она верна, — поставить её в ту же
измерительную оснастку, в которой производитель снимал цифры для даташита.
Поэтому у каждого компонента есть стенд, файл ожиданий и протокол сверки.

При этом библиотека жёстко разделяет **три уровня**:

1. `tests/` — универсальный regression компонента по даташиту;
2. `characterization/` — универсальные свипы и исследовательские стенды без
   привязки к одному изделию;
3. `applications/` — конкретные устройства со своими напряжениями, драйверами,
   токами, температурами и инженерными требованиями.

Напряжение питания конкретного клапана, номинал его мотора или выбранный MCU
не должны становиться «свойствами» модели MOSFET.

---

## Что нужно установить

**QSPICE** — https://www.qorvo.com/design-hub/design-tools/interactive/qspice
По умолчанию ставится в `C:\Program Files\QSPICE`.

**Git Bash** (идёт с Git for Windows) — в нём запускаются тесты.

Больше ничего. Python, PyQSPICE и прочее не требуются.

## Быстрый старт

Открыть Git Bash в корне библиотеки и выполнить:

```bash
chmod +x run_tests.sh     # один раз
./run_tests.sh
```

Ожидаемый вывод:

```
Najdeno stendov: 1
======================================================================

--- 74HCT244_test
    ECHO_CORNER    PASS
                   1 2 3 4
    A1_VOH         PASS
                   4.19999 3.97979 3.83999 3.70199
    A2_VOL         PASS
                   0.199806 0.259806 0.330006 0.400206
    ...
======================================================================
PASS: 12  WARN: 0  FAIL: 0
VSE STENDY PROSHLI BEZ PREDUPREZHDENIJ
```

`PASS` означает, что проверка прошла. `WARN` используется для типовых/nominal
точек: это качество фиттинга модели, а не гарантированная граница компонента.
`FAIL` означает нарушение hard-требования (гарантированный Min/Max даташита
или application requirement). WARN по умолчанию не роняет CI.

Если QSPICE установлен не по умолчанию:

```bash
QSPICE_DIR="/c/Qspice" ./run_tests.sh
```

Обратите внимание на запись пути: в Git Bash диск `C:` пишется как `/c/`.

Другие режимы:

```bash
./run_tests.sh 74HCT244      # прогнать только один компонент
KEEP_RAW=1 ./run_tests.sh    # не удалять .qraw, чтобы посмотреть осциллограммы
WARN_AS_FAIL=1 ./run_tests.sh  # строгий режим: WARN тоже возвращает exit 1
./run_tests.sh --all           # core regression + applications
./run_sweeps.sh FDS4559       # characterization sweep, CSV без PASS/FAIL; qraw удаляется
```

## Структура

```text
QSPICE_library/
├── README.md
├── run_tests.sh                  ← regression PASS/WARN/FAIL
├── run_sweeps.sh                 ← characterization -> .out + .csv
├── FDS4559/                      ← универсальный компонент
│   ├── FDS4559_N.txt
│   ├── FDS4559_P.txt
│   ├── datasheets/
│   ├── tests/                    ← только datasheet regression
│   └── characterization/         ← универсальные sweeps
└── applications/
    └── S6061NS-40DF/             ← конкретное изделие
        └── tests/
```

### Почему `tests/` и `characterization/` — не одно и то же

Regression отвечает на вопрос: **«модель воспроизводит спецификацию?»** и
имеет формальный PASS/WARN/FAIL.

Characterization отвечает на вопрос: **«как компонент ведёт себя при изменении
параметра?»**. Например, какой компромисс дают `Rg=22...1000 Ω` и
`fSW=10...400 kHz`. Универсального PASS для такого свипа обычно нет: один
проект выберет минимальные потери, другой — более мягкие фронты и меньший EMI.
Поэтому `run_sweeps.sh` формирует CSV, но не притворяется, что знает требования
будущего изделия.

### Где живут application tests

Конкретные `18 V`, `24 V`, M032, мотор, INA181 и температурный диапазон изделия
должны быть в `applications/<device>/`. Они могут использовать любые модели
библиотеки, но не загрязняют regression самого компонента.

По умолчанию `./run_tests.sh` прогоняет только core-компоненты верхнего уровня.
Application test запускается явно:

```bash
./run_tests.sh applications/S6061NS-40DF
```

или вместе со всем репозиторием:

```bash
./run_tests.sh --all
```


### Большие `.qraw` при characterization

`.meas` в QSPICE обрабатывается QPOST **после** создания `.qraw`. Поэтому
characterization-стенд должен сохранять через `.save` только те узлы/токи,
которые реально нужны измерениям. Иначе stepped transient может быстро
вырасти до сотен мегабайт, а QPOST будет долго разбирать файл и выглядеть как
зависший. `run_sweeps.sh` по умолчанию удаляет `.qraw` после построения CSV;
для отладки используйте `KEEP_RAW=1`.

## Как подключить модель к своей схеме

В netlist добавить строку загрузки и вызвать подсхему:

```spice
.lib C:\...\QSPICE_library\74HCT244\74HCT244.txt

X1 IN OEB OUT VCC GND 74HCT244 params: ROH=50 ROL=33.3 TPD=9n
```

Параметры, которые не указаны, берутся по умолчанию из `.subckt`.
Значения по умолчанию — типовые при +25 °C. Для анализа худшего случая
подставляйте набор из угла 4 (см. таблицу в шапке файла модели).

## Формат файла ожиданий

```
# izmerenie  rezhim  dopusk  ugol1 ugol2 ugol3 ugol4
A1_VOH       abs     0.03    4.20  3.98  3.84  3.70
A3_TPLH      max     0.15    14n   20n   25n   30n
```

| Режим | Условие | Когда применять |
|---|---|---|
| `abs` | \|изм − ож\| ≤ допуск | hard-требование по абсолютной величине |
| `rel` | \|изм − ож\| ≤ допуск · ож | hard-требование по относительной погрешности |
| `max` | изм ≤ ож · (1 + допуск) | гарантированные **максимумы** / application max |
| `min` | изм ≥ ож · (1 − допуск) | гарантированные **минимумы** / application min |
| `warn_abs` | как `abs` | типовая точка, качество nominal fit |
| `warn_rel` | как `rel` | типовая точка, качество nominal fit |
| `warn_max` | как `max` | диагностический мягкий предел |
| `warn_min` | как `min` | диагностический мягкий предел |

Суффиксы `p n u m k` понимаются. Если углов в строке меньше, чем шагов
`.step`, последнее значение используется для оставшихся.

Измерение, которого нет в файле ожиданий, помечается в выводе как
`net v .expect` — так вы не потеряете забытую строку.

### PASS / WARN / FAIL

Файл `.expect` теперь различает **спецификацию** и **качество модели**.
Типовое (`Typ`) значение даташита — не гарантия отдельного экземпляра, поэтому
его несовпадение не должно блокировать коммит, если модель остаётся внутри
гарантированных Min/Max. Для таких точек используются `warn_abs` / `warn_rel`.

Hard-режимы (`abs/rel/min/max`) предназначены для:

- гарантированных пределов даташита;
- требований конкретного проекта;
- safety/invariant-проверок стенда.

Итоговый код возврата:

```text
FAIL > 0                         -> exit 1
FAIL = 0, WARN >= 0             -> exit 0
WARN_AS_FAIL=1 и WARN > 0       -> exit 1
ошибка окружения                -> exit 2
```

Это позволяет CI не путать «типовая кривая смещена» с «модель нарушила
электрическую спецификацию».

### Regression, characterization и application

- **datasheet regression** (`<component>/tests`) воспроизводит измерительную
  оснастку производителя и имеет `.expect`;
- **characterization** (`<component>/characterization`) исследует параметрическое
  пространство и выдаёт измерения/CSV без универсального вердикта;
- **application test** (`applications/<device>/tests`) собирает реальный узел и
  проверяет инженерные требования конкретного изделия.

В `.expect` application-стенда должно быть явно написано, что цифры являются
требованиями проекта, а не параметрами из даташита.

## Как добавить новый компонент

1. **Создать папку** `<ИМЯ>/` с подпапками `datasheets/` и `tests/`,
   положить туда PDF даташита. Если нужны универсальные параметрические
   исследования — добавить `characterization/`.

2. **Написать модель** `<ИМЯ>/<ИМЯ>.txt` — один `.subckt`. В шапке обязательно:
   источник и ревизия даташита, версия модели, условия калибровки,
   таблица температурных углов и раздел «чего модель не воспроизводит».

3. **Написать стенд** `<ИМЯ>/tests/<ИМЯ>_test.cir`. Правило: стенд
   воспроизводит **условия измерения из даташита**, а не рабочую схему.
   Для каждой строки таблицы даташита — свой источник, своя нагрузка,
   своё `.meas`. Стенд только измеряет, никаких вердиктов.

4. **Заполнить ожидания** `<ИМЯ>/tests/<ИМЯ>_test.expect` прямо из таблиц
   даташита.

5. **Написать** `<ИМЯ>/tests/TEST_README.md` — для каждого измерения указать
   страницу, таблицу, строку и колонку даташита. Это самая скучная и самая
   ценная часть: через полгода только по ней можно будет понять, откуда
   взялась конкретная цифра.

6. **Прогнать** `./run_tests.sh <ИМЯ>` и калибровать параметры модели, пока hard-требования не станут `PASS`, а оставшиеся `WARN` не будут объяснены.

7. **Записать протокол** в `RESULTS.md`.

8. Не переносить внутрь компонента требования конкретного изделия. Для них
   создать `applications/<device>/tests/`.

Имя regression-стенда обязано заканчиваться на `_test.cir`. Универсальный
characterization-стенд — на `_sweep.cir`; его запускает `run_sweeps.sh`.

## Проверка «сломай нарочно»

Перед тем как поверить зелёным `PASS`, убедитесь, что стенд вообще способен
поймать ошибку. Испортите одно ожидание в `.expect` — должен появиться
`FAIL` с номером угла. Верните обратно.

Звучит избыточно, но именно так был пойман первый вариант вердиктов:
он показывал правдоподобные результаты, которые не имели отношения
к реальности.

## Автоматический прогон перед коммитом

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/usr/bin/env bash
./run_tests.sh || {
    echo "Стенды не прошли. Коммит отменён."
    echo "Если это осознанно: git commit --no-verify"
    exit 1
}
EOF
chmod +x .git/hooks/pre-commit
```

Скрипт возвращает 0 при успехе и 1 при любом провале, так что хук работает
без дополнительной обвязки.

## Особенности QSPICE, на которых легко споткнуться

Найдены экспериментально при работе над первым компонентом. В документации
частично есть, но разрозненно.

### `.meas` с TRIG/TARG требует условие уравнением

```spice
.meas TRAN TPLH TRIG V(pin)=2.5 RISE=1 TARG V(out)=2.5 RISE=1    ← так
.meas TRAN TPLH TRIG V(pin) VAL=2.5 RISE=1 ...                   ← ошибка
```

Форма с `VAL=` (как в LTspice) даёт `Expected lhs=rhs`.

### `.meas ... PARAM` при `.step` считает неверно

Строка вида

```spice
.meas TRAN PASS PARAM {if(abs(A1_VOH-VOH_EXP)<0.03,1,0)}
```

выглядит работающей, но при `.step` **параметр внутри выражения заморожен
на значении последнего шага**. Схема при этом степается правильно.

Проверено: при полном совпадении всех четырёх измерений с даташитом
вердикт выдал `0 0 0 1` — «прошёл» только тот угол, чьё ожидаемое значение
случайно совпало с замороженным. Ошибка молчаливая, никаких предупреждений.

Поэтому сравнение вынесено в `run_tests.sh`.

### `.model` ключа пишется без скобок, параметры обязательны

```spice
.model SWUP SW Ron=50 Roff=1g Vt=2.75 Vh=0.2
```

Значений по умолчанию для `Ron`, `Roff`, `Vt`, `Vh` у QSPICE нет.

### TTOL на разрывных элементах

QSPICE считает с адаптивным шагом. Ключи `S` и `if()` в B-источнике —
разрывные: момент переключения находится точно, но **следующая** точка
может оказаться далеко, и `.meas` начинает интерполировать мимо.

Проверено на 74HCT244 без ограничения шага в `.tran`:

```
TTOL=1n    → tPLH = 14,94 нс
TTOL=200n  → tPLH = 16,97 нс   (+14 %)
```

Важная деталь: фронты при этом не искажаются — они сами заставляют решатель
мельчить. Страдают только измерения **по одному пересечению уровня**,
то есть задержки. Картинка выглядит нормально, а число врёт.

### `.temp` / `.step temp` не создают температурную зависимость в поведенческой модели

Температурной зависимости у них нет. Температура входит **набором
параметров** — так же, как даташит задаёт её отдельными колонками
гарантированных пределов.

Число углов диктуется даташитом, а не привычкой. У 74HCT244 их четыре
(`Typ` плюс три температурных диапазона), у ULQ2003A — два (`Typ` и `Max`
при 25 °C, колонок по температуре нет). Растягивать второй до четырёх
означало бы выдумывать данные.

## Запуск вручную, без скрипта

```bash
cd 74HCT244/tests
"/c/Program Files/QSPICE/QSPICE64.exe" -binary 74HCT244_test.cir
"/c/Program Files/QSPICE/QPOST.exe" 74HCT244_test.cir -o out.txt
cat out.txt
```

Посмотреть осциллограммы: `"/c/Program Files/QSPICE/QUX.exe" 74HCT244_test.qraw`

Пересчитать измерения по уже готовому `.qraw`, без повторной симуляции:

```bash
"/c/Program Files/QSPICE/QPOST.exe" meas_script.txt -r 74HCT244_test.qraw -o out.txt
```

Первая строка файла `meas_script.txt` обязана быть комментарием — она
игнорируется. Удобно при подборе критериев годности: прогон с шагом
0,05 нс не бесплатный.

| Компонент | Версия | Даташит | Статус |
|---|---|---|---|
| 74HCT244 | 1.1 | onsemi MM74HCT244/D Rev.3, June 2024 | 8 измерений × 4 угла, все в допуске |

> **ULQ2003A, а не ULN2003A.** Электрически они идентичны, но рабочий
> диапазон разный: ULN от −20 °C, ULQ от −40 °C. Для привода заслонки
> с −30 °C годится только ULQ. Модель температуру не воспроизводит
> и такую ошибку не поймает — проверять по спецификации.
